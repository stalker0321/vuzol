# Исполнение, независимый лид и прозрачность входящих поручений

Владелец 2026-10-22 поручил последовательно реализовать этот фронт работ без
ожидания дополнительных ответов. Работать поверх существующей системы, без
переписывания архитектуры. Документ фиксирует требования и проверяемый прогресс.

## Что произошло

MCP принял goal a034b561-807f-428a-9b3d-788d692c5dce в lead-ui-pilot-20261021.
Один ход Muse создал пакет и одну coding-задачу c432c884-6f60-45ba-959d-1fdc7eb0d7bb.
DeepSeek выполнялся 00:37–01:13 UTC; пользователь наблюдал повторные обращения
к модели внутри этого запуска. Функция и тесты сохранились в worktree, семь
unittest проходят при отдельной диагностической проверке. Это не завершённая
задача: штатные validation, review и интеграция не состоялись.

Причина внутренних повторов неизвестна: остановка runtime выбрасывала исключение
и теряла накопленный stdout до complete(). Затем сохранение рабочего дерева
через retain() упало с ArtifactSecretError. В дереве обнаружен .tmp-safe-chain
с собственным CA/private key; ключ подходит под встроенный фильтр diff. Ранее
озвученное предположение, что именно запись stdout отвергла ключ, неверно:
ArtifactStore.persist() редактирует секреты; reject_secrets вызывается в retain().

Вопрос пользователя 00:58 UTC ждал тяжёлую очередь до 01:13, затем выбрал codex-a
при проектном allowlist только opencode.ai и упал в proxy_targets. Две следующие
попытки ответа отвергнуты из-за оставшегося durable account ticket. OpenCode и
Codex tickets остались заняты, хотя активных процессов провайдера уже нет.

С 04:37 UTC executor перезапускается на validation preflight. Настроенный digest
vuzol-validation отсутствует в его rootless Docker. Это более поздняя поломка,
не доказанная причина исходного 36-минутного исполнения.

## Последовательность реализации

1. Восстановить validation image и готовность executor без отключения preflight.
   Сохранить существующие worktree и результаты. Освобождать старые account
   tickets только после fencing владельца и проверки отсутствия живого runtime.
   Исправить утечки на ошибках до запуска и независимость cleanup от артефактов.
2. Сохранять историю во время работы, а не только в конце. Нужны вход, назначения
   моделей, каждый provider/tool event, результаты/ошибки инструментов, retry,
   пауза, завершение, расходы и причины ожидания. Связать request/goal/package/
   task/step/invocation. Приватные сырые данные хранить с ограниченным доступом;
   ключи и токены не выводить в Telegram и обычный диагностический просмотр.
   Ошибка записи одного артефакта не должна стирать всю историю или блокировать
   освобождение уже завершённого процесса. Секретный фильтр не отключать.
3. Лид и разговор не должны стоять за долгим исполнителем. Один аккаунт не
   равен одному процессу на весь Вузол. Разделить реальную пропускную способность
   аккаунта и владение изменяемым локальным состоянием CLI. Обеспечить независимые
   состояния конкурентных invocations и резерв управления при занятых воркерах.
   Проверять admission по фактическим возможностям провайдера; реальные 429 и
   ограничения должны давать понятное ожидание, а не менять аккаунт молча.
   Не обходить ограничения ложными account_id и не просто удалить блокировки.
4. /lead должен действительно обращаться к лиду. Проверять сетевую совместимость
   до назначения; обычный вопрос о ходе работы не должен запускать git-worktree
   за долгой coding-задачей. Статус доступен даже при недоступности модели.
   Показать, какой шаг, модель и инструмент работают, сколько времени и что
   последний раз изменилось. Повторы без прогресса должны быть заметны лиду.
5. На каждое принятое внешнее поручение отправлять отдельное сообщение в топик:
   источник (ChatGPT/MCP, личный ассистент Telegram или прямое поручение),
   авторизовавший владелец, проект, request/goal ID и исходный текст, который
   реально поступил в Вузол, scope и критерии. Затем обычные карточки прогресса.
   Источник выводить из доверенного ingress/OAuth client, не из заявления модели.
   Запись входящего поручения и постановка уведомления — атомарно с принятием;
   повтор того же request_id не создаёт второй goal или второе уведомление.
   Сохранить полный текст, дробить длинные сообщения, экранировать разметку.

## Как принять результат

- Ошибка сохранения stdout, исключение до spawn, pause и restart не оставляют
  необъяснимый вечный busy; при неопределённости есть запись и путь reconciliation.
- После принудительного обрыва доступна история до обрыва, включая обращения
  модели и tool results; по ней можно увидеть цикл и его причину.
- При занятом DeepSeek тот же реальный OpenCode-аккаунт допускает независимый
  вызов лида в пределах проверенной concurrency; его state не повреждается.
- /lead и вопрос о статусе обслуживаются при долгом/зависшем worker; модель
  получает актуальные факты, а не предположение, что всё ещё выполняется.
- Одно поручение MCP даёт читаемое исходное сообщение в Telegram; повтор
  submission, перезапуск и временная недоступность Telegram не теряют сообщение
  и не размножают поручения. Сохранить доказательства исходного текста и источника.
- Итоговый живой ограниченный прогон: вход из MCP → уведомление → worker →
  вопрос лиду во время исполнения → pause → подтверждённая остановка/cleanup.

## Журнал выполнения

- Диагностика завершена; production во время диагностики не изменялся.
- Реализация начата после прямого поручения владельца.

## Что реализовано и выложено

Релиз `t136-execution-reliability-r5`, поверх `f5a3422` с незакоммиченными
изменениями этого рабочего дерева. Executor: `/opt/vuzol/releases/t136`.
Core и MCP работают на одном новом образе; executor, applier и publisher используют
тот же source release. Старые MCP Python-overlay больше
не подменяют отдельные модули. БД обновлена до `e8b5a61fa505`: прежний production
не содержал эту миграцию и реализацию `/think`/`/lead`.

1. Восстановлен validation image, без отключения стартовых проверок. В provider
   image добавлен настоящий Python: раньше PATH содержал только Safe Chain shims,
   а базовый Node image не содержал интерпретатор. Safe Chain получает отдельный
   invocation-local tmpfs для CA, вне worktree; защита установки пакетов сохранена.
   `python -c 'import unittest'` проверен при закрытой сети и read-only rootfs.
   Это правдоподобное объяснение повторов исходного запуска, но не доказанная
   единственная причина: его старый stdout уже потерян.
2. Runtime пишет вход, argv/изоляцию, stdout/stderr по мере получения, время,
   порядковые номера записей и итог cleanup в append-only AES-GCM journal.
   Журнал доступен до завершения процесса, переживает неполный последний frame.
   В частности, Pi JSONL содержит события моделей, инструментов и их результаты.
   Сохраняется то, что реально выдаёт CLI: невидимые внутренние действия самого
   сервиса-провайдера восстановить нельзя. Идентификаторы связывают журнал с
   task/run/step, поколением lease и provider attempt. БД сохраняет назначение,
   приём входящего запроса, результаты и учёт использования отдельно.
3. Подтверждение завершения launcher/container/proxy сохраняется отдельно от
   транзакции записи артефактов. Ошибка артефакта не превращает доказанно
   завершённый процесс обратно в unknown. Отмена и повторная отмена ожидают
   cleanup; внешний proxy-monitor больше не выбрасывает полученный partial
   receipt. Неопределённый исход по-прежнему не разрешает слепой повтор.
4. Lead, read-only conversation, preparation conversation worktree, review и
   тяжёлые работы обслуживаются независимыми executor loops. Conversation steps
   относятся к LIGHT, а не HEAVY. Для реального `opencode-go-c`: два слота,
   один зарезервирован для управления. Воркеры его занять не могут. Это не два
   вымышленных account_id и не отключение admission/429.
5. Pi использует readonly canonical seed и собственный `/tmp/pi-home` на каждый
   запуск. Копируются auth/models/settings; общий файл авторизации не меняется.
   Данный OpenCode seed использует API key, не OAuth-refresh. Другие CLI с
   изменяемым OAuth-state не объявлены безопасными для concurrency > 1.
6. Несовместимость выбранного разговорного профиля с проектной сетью выявляется
   до создания/запуска ответа, с явным сообщением вместо молчаливой подмены модели.
   Trusted pre-launch rejection освобождает account ticket; произвольное
   исключение не считается доказательством, что provider не запускался.
7. Входящий внешний goal атомарно сохраняет provenance, audit event и Telegram
   outbox с полным исходным request/scope/criteria. Источник берётся из ingress и
   проверенного OAuth client; для настроенного клиента — ChatGPT. Повтор
   request_id после restart не дублирует goal/notice. Длинные сообщения идут через
   существующую подтверждаемую последовательность частей. Прямой Telegram-текст
   второй раз не копируется: он уже виден пользователю; аудит сохраняется.
   Provenance не входит в semantic idempotency hash: старый receipt без него
   и retry после переименования OAuth client остаются совместимыми. Исходный
   источник первого принятого запроса при retry не переписывается.
8. Статус и read-only chat получают реальные состояния дочерних задач, шага,
   профиля, процесса, длительность и флаг неизвестного runtime outcome.
9. Дополнительно живой прогон нашёл и закрыл два разрыва: seed_trial затирал
   frozen project model assignments; pause запрещался state machine для BLOCKED.
   Теперь snapshot сохраняется, BLOCKED можно поставить на паузу, а resume не
   стирает исходный blocker и не разрешает его автоматический retry.

Во время выкладки обнаружены ещё две эксплуатационные зависимости: registry
без секретов должен читаться UID core-контейнеров; Compose необходимо запускать
с явным `--env-file /srv/vuzol/.env`. Иначе пропадает Telegram token. Это
исправлено; release deploy helper проверяет наличие нужных секретов до recreate
и сохраняет прежние users/mounts. Значения секретов в отчёт не выводились.

- Validation image:
  `vuzol-validation@sha256:0c17d7ff573ae4a3d840c3aa4b6a3cc4a811b6d11f8433b649697e31e611ce40`.

  Они вынесены за artifact_root, чтобы orphan-sweeper не удалял историю.

  Старые account tickets сняты через fencing, проверку runtime и точный token,

- Старый `.tmp-safe-chain` с CA/key перемещён из исходного worktree в закрытый

  Он не удалён; рабочие изменения кода не затронуты.

## Что не следует считать законченным

- Не доказано, что система больше никогда не зациклится. Теперь сохраняется
  материал для разбора и работает управление во время worker turn. Автоматический
  semantic loop detector/перепланировщик поверх tool errors здесь не добавлялся.
- Concurrency проверена для Pi/OpenCode C, а не для каждого возможного провайдера.
  Общая HEAVY concurrency оставлена ограниченной ресурсами узла; это не обещание
  бесконечного числа одновременно работающих coding sandbox на 4 ГБ RAM.
- Старые сертификаты Grok/Codex из августа были привязаны к уже неиспользуемому
  образу ещё до этой работы. Текущие DeepSeek C и Codex A квалифицированы заново.
  Дополнительные canary Grok A/B пока не прошли: A остановлен budget policy;
  B дал exit 1, затем budget_exhausted. Их нельзя выдавать за рабочие runtime
  certificates. Произвольные потолки расходов не повышались автоматически.
- Синхронизация названия одного старого Telegram topic всё ещё даёт warning;
  сама ingress application и delivery работают. Внешний Telegram API не
  объявляется безошибочным.
- В двух pilot-проектах сеть ограничена `opencode.ai`. `/lead` с Muse совместим;
  `/think` с глобальным Sol требует отдельного разрешённого upstream endpoint
  или другого явно выбранного think-профиля. Система теперь объясняет отказ,
  не подменяет модель и не держит account slot. Сетевые права пилотов здесь
  самовольно не расширялись.

- Финальный полный unit suite: 3540 passed, 1 skipped.

  controls: 302 passed, 11 skipped, на отдельной временной БД. Дополнительный

  35 passed. Production DB не очищалась тестовыми fixtures.
  Изолированная БД — `vuzol_reliability_test_20261022` в `writer-postgres-1`;

- Scoped strict mypy: 11 source modules + idempotency command module — pass.
  Ruff для изменённого кода — pass; `git diff --check` — pass.
- Общерепозиторные lint/format не объявляются полностью зелёными: есть
  существующий SIM105 в execution/git.py и ранее неформатированные файлы.
  Массовое форматирование чужого кода не проводилось.
- Validation image собран с dependency audit; certifi/pypdf обновлены до
  исправленных версий также в core image и host release venv.

При включении проверки disjoint storage roots обнаружилось, что production
использует родительский artifact_root, а не предполагаемый дочерний каталог.
Executor отказался стартовать, как и должен при такой конфигурации. Журналы
целиком перенесены из `/srv/vuzol/artifacts/runtime-journal` в
`/srv/vuzol/runtime-journal`, обновлены systemd environment и ReadWritePaths.
Записи не удалялись. Этот отказ во время выкладки присутствует в journalctl;
его нельзя путать с исходным ночным incident или выдавать за отсутствие рестартов.
