# Мониторинг публичных источников

Монитор работает в процессе interpreter и по умолчанию выключен. Сейчас он читает
RSS 2.0/Atom, GitHub releases, поиск историй Hacker News и новые посты Reddit без
авторизации. HTTP-запросы ограничены 20 секундами и 2 МБ распакованного ответа;
редиректы разрешены только на тот же хост. XML с DTD или entities отклоняется.
Ошибка одного источника записывается в лог и не останавливает остальные.

Настройки доступны как `settings.monitor`, переменные окружения — с префиксом
`VUZOL_MONITOR__`. Чтобы включить монитор, задайте `ENABLED=true`, `CHAT_ID`,
`MESSAGE_THREAD_ID` темы «Мониторинг», `PROFILE_IDS` и `INTERESTS`. `PROFILE_IDS` —
JSON-массив ID существующих модельных профилей в порядке основной/резервные;
цепочка строится так же, как у inbox и ассистента. Часовой пояс и параметры
модельных вызовов берутся у ассистента. Его самого включать необязательно.

Например, добавьте источник через `VUZOL_MONITOR__SOURCES`:

```json
[
  {
    "id": "python-releases",
    "kind": "github_releases",
    "target": "python/cpython",
    "interval_minutes": 60,
    "include": ["Python"],
    "exclude": ["preview"]
  }
]
```

`id` должен быть уникальным и постоянным. Для `rss` target — URL ленты;
для `github_releases` — `owner/repo`; для `hn` — поисковая строка;
для `reddit` — имя subreddit без `r/`. `include` оставляет записи с хотя бы одним
словом/фразой в заголовке или выдержке, `exclude` отбрасывает совпадения.
Регистр не учитывается. Пустые списки отключают соответствующий фильтр.

До модели удаляются дубли по источнику и внешнему ID, повторы URL между
источниками и записи старше семи дней. Отброшенные записи хранятся с причиной;
выдержки ограничены 4000 символами. Время успешной загрузки хранится в БД,
поэтому перезапуск не сбрасывает интервалы. При ошибке загрузка повторяется
на следующем проходе. Записи без даты публикации допускаются.

Модель получает интересы владельца и до 20 записей за вызов. Тексты источников —
недоверенные данные, а не инструкции. Ответ содержит оценку 0–1, однострочное
русское резюме и причину. Невалидный ответ оставляет весь пакет в `new` до
следующего прохода.

`DIGEST_HOURS` по умолчанию `[9, 21]` в часовом поясе ассистента. В эти часы
монитор отправляет одно сообщение с ещё не отправленными записями с оценкой
не ниже 0.6, группируя их по источникам, максимум 15. Длинный дайджест использует
rich message; явный отказ переключает его на обычный HTML. Размер подборки
ограничен так, чтобы fallback помещался в одно сообщение с заголовками, резюме
и ссылками. Остаток ждёт следующего часа рассылки. Пустых сообщений нет.

Перед отправкой фиксируются часовая отметка и потреблённые записи. Таймаут,
потеря ответа или остановка после фиксации не приводят к повторной отправке,
даже в следующий час. Это означает возможную потерю дайджеста при аварии перед
отправкой. В `monitor_digests` видны состояния `reserved`, `sent`, `ambiguous`;
`digested_at` заполняется только при подтверждении Telegram. Автоповтора для
неоднозначной доставки нет.

Миграция создаёт `monitor_events`, `monitor_source_fetches`, `monitor_digests`.
В production compose добавлен только pass-through флага
`VUZOL_MONITOR__ENABLED` с default `false`; остальная конфигурация монитора
должна быть передана interpreter через настройки окружения отдельно.

Отложены до следующих этапов: Gmail, Calendar, X/Apify (нужны credentials),
глубокий анализ, редакционная память и извлечение действий. Монитор сам не
создаёт задачи и не выполняет инструкции из источников.
