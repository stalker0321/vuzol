# Вузол: агент, который ведёт работу, поверх работающего ядра

План для реализации Гроком. 19 октября 2026. Статус: предложение для обсуждения; не разрешение на production rollout.

## 1. Что хотим получить

Пользователь пишет в проектный или общий Telegram-топик: «хочу вот такой результат». Агент уточняет существенную неопределённость, сохраняет цель и критерии готовности, организует работу, получает результаты, исправляет выявленные проблемы и возвращается с результатом либо конкретным запросом решения. Пользователь не должен вручную запускать каждый следующий шаг.

Агент не обязан непрерывно думать. Он просыпается на новые сообщения, завершение работы, появление разрешения или истечение осмысленного таймера. Между событиями система не тратит inference на проверку, не изменилось ли что-нибудь.

Главное разделение: **модель решает, что делать дальше; ядро решает, допустима ли команда, и надёжно исполняет её**. Не заменяем инфраструктурные гарантии промптом. Не превращаем модель в ремонтника базы и хоста.

Первый полезный результат — один агент доводит одну согласованную цель в существующем проекте через несколько участков работы, переживает рестарт, не требует владельца между безопасными шагами и останавливается перед неделегированным действием.

## 3. Архитектура и границы ответственности

```text
Telegram: общий inbox / проектный топик
                   |
       маршрутизация сообщения → конкретная цель
                   |
       агент-руководитель проекта (решения)
                   |
       типизированные команды + серверная авторизация
                   |
       существующие packages / tasks / workflows
                   |
       исполнение → проверка → эффекты / результаты
                   |
       сохранённые события → следующий ход агента
```

### 3.1. Один движок, две области полномочий

Проектный руководитель видит цели и разрешённые ресурсы конкретного проекта. Общий помощник видит inbox и разрешённый каталог проектов, умеет уточнить и маршрутизировать поручение. Он не становится вторым руководителем уже переданной работы.

Не держать отдельный вечный процесс модели на каждый топик. Агент — долговечная запись состояния и обработчик событий. Назначение модели — конфигурация роли, а не источник привилегий. Замена провайдера не расширяет права.

Первоначально один активный руководящий ход на проект; несколько целей можно хранить в очереди. Разные проекты могут продвигаться независимо. Одновременное изменение одного репозитория отложено до отдельного этапа интеграции.

### 3.2. Не путать цель, пакет исполнения и Telegram-топик

Цель живёт дольше одного плана или task. Минимальная новая сущность `ManagedGoal` содержит project/owner, исходный запрос, версию согласованного scope, критерии готовности, ограничения, lifecycle, ссылки на текущий пакет и результаты. Lifecycle цели не копирует статусы всех дочерних tasks: их читаем из существующего источника правды.

Предлагаемый lifecycle: `draft → active ↔ waiting`, отдельно `paused`, терминальные `completed/cancelled`. У `waiting` обязательны причина и условие пробуждения: worker, owner, capability, quota, reconciliation. Ошибка инфраструктуры не превращается в «цель достигнута».

План — версионированное представление пути к цели, не обещание исполнить первоначальный список любой ценой. Руководитель может менять следующие действия в рамках согласованного результата; расширение scope или ослабление критериев требует владельца. Активный пакет не переписывается задним числом.

Источник поручения и адрес уведомлений хранятся отдельно от ownership исполнения. Общий топик может содержать несколько независимых поручений. Reply и короткий ID цели однозначно выбирают поток; неоднозначное «сделай так» вызывает вопрос, а не случайный выбор последнего проекта.

В первом срезе цели привязаны к существующим проектным sessions. Общий inbox позже получает собственные записи intake/routing, **не фиктивные Telegram thread IDs и не снятие `uq_live_work_package_session`**. Исполнение поручения из inbox идёт в существующую проектную session, ответ можно возвращать в inbox. Полное отсутствие проектного топика — отдельная последующая миграция внутренних execution sessions, не скрытая предпосылка первого релиза.

### 3.3. Единственный владелец следующего шага

На первом этапе руководитель работает **над пакетами**, а не заменяет sequencer:

- Агент выбирает следующий небольшой пакет, часто из одного элемента, и запускает его через командный слой.
- Sequencer единолично назначает элементы внутри этого пакета; workflow единолично ведёт его внутренние шаги.
- Пока пакет исполняется или имеет незавершённые/неопределённые эффекты, агент не запускает конкурирующий пакет и не дублирует внутренние retry.
- После окончательного результата агент выбирает: следующий пакет, разрешённая доработка, вопрос владельцу или проверка готовности цели.
- Ревью и повторная работа внутри существующего workflow остаются там. Агент вмешивается после исчерпания его штатного восстановления или при необходимости нового плана.

Ввести явное ownership для managed goal/session и атомарный admission fence. Legacy-путь и агентный путь проверяют один и тот же fence при старте работы. Связь goal → package и запуск записываются в одной транзакции; нельзя сначала запустить пакет, а потом пытаться привязать его к цели.

Ручная новая задача в занятом проекте не теряется: поставить в очередь или предложить владельцу приостановить текущую цель. Перехват владения — явная команда на безопасной границе. Старые задачи не переводить автоматически в managed mode. Не добавлять одновременно второй «agent sequencer».

Это сознательный компромисс: не вся свобода сразу, зато адаптивное движение между небольшими пакетами без переписывания проверенного внутреннего исполнения.

## 4. Командный слой: API-like без обязательного нового HTTP-сервера

Начать с application service и typed tool adapter внутри существующего приложения. Telegram, CLI и модель вызывают одни доменные команды. HTTP можно добавить потом; сетевой API сам по себе проблему orchestration не решает.

Пример минимального каталога:

| Команда | Смысл и обязательное ограничение |
| --- | --- |
| `get_goal`, `get_project_state`, `get_capabilities`, `get_result` | Только авторизованный scope, результаты с версиями и evidence refs |
| `request_plan` | Учтённая планировочная работа, возвращает job ID; не запускает исполнение сама |
| `propose_batch`, `start_batch` | Цель, scope revision, текущая версия, поддерживаемый work domain; запуск по делегированному policy |
| `request_revision` / штатные retry-controls | Ссылка на конкретные findings и candidate; не обход retry policy и неизвестных эффектов |
| `request_permission` | Создать один дедуплицируемый запрос владельцу, не выдать себе permission |
| `request_capability` | Потребность в инструменте; установка через provisioner и отдельное разрешение |
| `wait_for` | Сохранить условие ожидания; не busy loop модели |
| `propose_completion` | Запросить проверку критериев цели на конкретных результатах |
| `pause_goal`, `cancel_goal` | Штатная остановка дочерней работы, без обещания отменить уже совершённый внешний эффект |

Каталог показывает только реально поддерживаемые операции. Не объявлять research/AVD/deploy рабочим инструментом, пока нет handler, sandbox, evidence и проверки его маршрута. Неподдерживаемый запрос возвращает `unsupported_capability` с понятным следующим действием.

Для каждой изменяющей команды: server-derived actor, goal/project scope, версия контракта, expected entity/scope version, idempotency key, typed payload, краткая причина и ссылки на основание. Модель не выбирает credentials, role, policy revision или собственную личность. Контекст вызова назначает сервер.

Ответ: `applied | duplicate | stale | denied | waiting | unsupported`, authoritative IDs/versions и структурированная причина. Плюс current state, если это допустимо. Ошибку модели не превращать в traceback для пользователя и не маскировать под успешный результат.

Idempotency key привязан к actor + команде + target + hash payload. Повтор того же вызова возвращает исходный receipt. Тот же ключ с другим payload — конфликт. Проверка версии, полномочий, fence и запись команды/события атомарны. Долгие внешние операции — через сохранённый intent/outbox, не внутри транзакции БД.

## 5. Полномочия и приёмка

Добавить типизированный human/agent principal. Сохранить совместимость существующих human callers через адаптер, не выдавать модели фиктивный `user_id` владельца. Проверка действует не только в tool wrapper, но в общей command boundary. Проверить task, package и approval endpoints, включая CLI и Telegram.

Делегирование задаёт владелец: проект, scope цели, разрешённые действия и targets/environments, срок/отзыв, policy revision. По умолчанию агент не получает никаких новых mutation-полномочий, пока владелец не включил managed mode с понятной политикой.

Рекомендуемая первая политика:

- Можно: планирование, чтение в своём scope, запуск работ в изолированной рабочей области, проверки, разрешённые доработки, применение проверенного результата в выделенную integration branch.
- Только отдельное разрешение владельца: production deploy, изменение защищённой/default ветки в первом пилоте, новая установка на хост, секреты/права/egress, создание платных ресурсов, удаление данных, исключения из safety policy.
- `accept_criterion` при отсутствии доказательств, `accept_uncertainty`, `admit_ceiling`, `reconcile_cost` не выдавать агенту автоматически. Это решения владельца о риске/учёте, а не обычное «ревью прошло».

Разрешение действовать ≠ доказательство качества ≠ согласие на исключение. Все три вещи хранить отдельно. Руководитель не может сам написать PASS и закрыть критерий. Существующая независимая проверка остаётся обязательной там, где её требует domain policy.

Чтобы не застревать после каждого одноэлементного пакета: добавить **узкое policy-based разрешение финального результата пакета в выделенную managed integration branch**, если текущие gates/review пройдены и approval envelope совпадает. Сейчас последний элемент отличается от промежуточных; это место надо обработать явно. Не объявлять последний элемент «промежуточным» ради обхода и не разрешать этим default/prod apply. Проверки следующего пакета должны использовать фактический head integration branch.

Human approval и agent command могут использовать один service, но разные решения авторизации. Кнопка Telegram не является удостоверением владельца: проверяется фактический sender, конкретный action envelope, актуальность и срок. Отзыв delegation блокирует ещё не начатые эффекты на их execution boundary; уже выполненное только учитывается и показывается.

Документы, репозиторий, результаты research и ответы работников — недоверенные данные. Они не могут изменять policy, подтверждать consent или создавать trusted owner message. Доступ к общему inbox не даёт право читать все секреты всех проектов.

## 6. Надёжный цикл руководителя

Минимальные долговечные данные, предпочтительно поверх имеющихся механизмов:

- Goal, версии scope/критериев и связь с пакетами.
- Agent scope/ownership и текущая lease с fencing epoch.
- Входящие события и checkpoint обработанного состояния.
- Turn receipt: входные версии, модель/profile, usage, решение, tool calls/results.
- Delegation и command receipts. Не дублировать уже имеющийся event/effect/accounting ledger.

Обработчик: claim → загрузить authoritative snapshot → вызвать модель вне DB-транзакции → сохранить результат хода → проверить актуальность → применить допустимые команды → сохранить ожидание/следующее событие. Lease renewal и время провайдера должны согласовываться. Если lease потеряна, старый ответ не может изменить состояние.

Доставка событий at-least-once. Добиваемся однократного логического эффекта через дедупликацию и effect reconciliation, а не обещанием exactly-once для внешних API.

Обязательные случаи:

- Crash до вызова, после ответа, после commit команды и до acknowledgement: восстановление не теряет работу и не запускает второй пакет.
- Два wakeup одновременно: один активный turn на scope; остальные события не теряются.
- Старый ответ после pause/cancel, изменения цели или отзыва прав: отказ мутации и загрузка нового состояния.
- Внешний эффект мог произойти, но ответ потерян: reconciliation, не слепой повтор.
- `wait_for` и подписка на событие фиксируются без lost wakeup: уже завершившийся job сразу виден; периодический reconciler поднимает пропущенные уведомления из authoritative state.
- Пока агент ждёт владельца, другие проекты работают. Не держать lease или транзакцию всё время ожидания человека.

Память — резюме для удобства, не источник permissions, статусов или результатов. Контекст формируется из цели, текущих команд/артефактов, blockers и последних решений. Длинная история сворачивается с сохранением ссылок на исходные данные; после рестарта руководитель восстанавливается без «памяти процесса».

## 7. Лимиты и деньги

Не ставить произвольный общий лимит, превышение которого объявляет цель проваленной. Разделить:

1. Технические ограничения вызова: контекст, output, timeout, concurrency. Они нужны для устойчивости и должны соответствовать конкретному адаптеру.
2. Мягкая оценка расхода: предупреждение и пересмотр прогноза. Превышение само по себе не отменяет цель.
3. Явно выбранный владельцем денежный предел: запрет новых расходов/ожидание решения при исчерпании, сохранение результата и возможность продолжить. Не выдавать грубую CLI admission-оценку за точную гарантию потолка.
4. Защита от бесполезного цикла: повтор одинаковой ошибки/плана без новых доказательств вызывает переоценку или вопрос, а не бесконечное списание.

Порог повторов конфигурируемый, со смыслом и тестами, а не спрятанный «ещё 20 попыток». Неограниченные repair-inference запрещены. Неизвестный cost остаётся неизвестным; агент не записывает ноль и не «согласует» его за владельца. Учитывать отдельно руководство, планирование, исполнение и ревью; подписку не изображать API-расходом без корректной модели учёта.

## 8. Готовность цели, тестирование и параллельная работа

Критерии должны описывать наблюдаемый результат, а не «выполнить все придуманные таски». Пакеты закончились — ещё не значит, что цель достигнута. Проверка завершения использует актуальную версию критериев и evidence конкретных артефактов; отклонённый или superseded candidate не подходит.

Код проверяется на commit/build, который реально предлагается применить. Android-сценарий фиксирует build identity, AVD image/device/config, сценарий, logs/screenshots и результат. Research может завершиться отчётом с источниками и обозначенной неопределённостью; нельзя требовать от него coding gates или считать непроверенный текст достаточным для произвольных заявлений.

В первом пилоте один изменяющий пакет на проект. Позже разрешить параллельные независимые read-only jobs, затем несколько worktrees. Для каждого job: входные версии/артефакты, зависимости, outputs, resource claims. AVD, deployment target и integration branch требуют реального mutual exclusion. Lease expiry не освобождает опасный ресурс, пока старый процесс не остановлен либо надёжно fenced.

Один integration owner сериализует merge/apply. После rebase/conflict resolution проверки запускаются на новом результате. Параллельное тестирование старого APK не подтверждает новый APK. Одновременные commits в разные worktrees сами по себе не гарантируют независимость задач.

## 9. Этапы реализации и критерии выхода

### Этап 0 — сохранить рабочую точку и установить факты

До новой архитектуры:

- Проверить весь tracked/untracked diff, зафиксировать владельцу состав baseline. Не включать секреты, runtime data и посторонние файлы через слепой `git add .`.
- С согласия владельца сохранить текущие изменения в baseline commit и отметить точку восстановления; работать в отдельной feature branch. Само создание ветки незакоммиченный baseline не фиксирует. Не stash/reset пользовательские изменения автоматически.
- Записать baseline SHA, dirty status, версии config/schema и реально используемый runtime/release. Код в этом каталоге не обязательно равен запущенному сервису.
- Проверить baseline unit/integration и текущий task→test→approval flow в изолированной среде. Production smoke не выполнять без отдельного разрешения. Имеющиеся сбои перечислить отдельно, не присваивать новому коду и не скрывать.
- Составить краткую карту существующих command/approval/event/lease механизмов и точных мест ownership fence. Если модель плана здесь не соответствует коду, написать расхождение до реализации спорной части.

Выход: воспроизводимая рабочая точка, результаты проверок, безопасная тестовая среда. Если baseline не сохранён или тестовая БД не идентифицирована — остановиться до изменений архитектуры.

### Этап 1 — единая авторизация и узкий командный фасад

Добавить human/agent principal, явное delegation, typed command receipts, idempotency/version checks и минимальный каталог чтения/запуска. Сохранить существующий human API. Новые agent mutations выключены по умолчанию.

Выход: одна допустимая команда проходит через human/agent adapters с корректным audit; недопустимая не проходит ни через один обходной путь. Покрыты отзыв прав, stale version, повтор и collision ключа. Никаких автономных новых workers пока.

### Этап 2 — один руководитель, одна цель, существующий проект

Добавить ManagedGoal, ownership fence, event-driven turn, ожидания и восстановление. Переиспользовать provider routing/accounting и outbox. Реализовать управление небольшими пакетами и безопасную integration-branch приёмку из раздела 5. Telegram: включение managed goal владельцем, прогресс, pause/resume/cancel, вопросы и итог.

Главный тестовый сценарий: цель → план → пакет A → review требует доработку → штатная доработка → проверенный результат A → агент выбирает пакет B → проверенный результат B → подтверждение критериев цели. Итоговая публикация/защищённая ветка остаётся owner boundary. Между A и B — рестарт процесса. Никакого ручного SQL, вызова внутренних методов вместо входных adapters или ручного «подпихивания» задания.

Выход: сценарий проходит через реальные application services, PostgreSQL, очередь/worker и Telegram ingress с fake provider и fake transport; fault injections подтверждают раздел 6. Feature-off legacy-сценарий остаётся рабочим. Это **основной рубеж первой ночи**, не обещание, что его обязательно удастся закончить за ночь.

### Этап 3 — общий inbox, без второго оркестратора

Добавить intake/routing, reply-to/goal ID, список активных поручений, передачу существующему project lead и обратные уведомления. Новое поручение в занятом проекте становится отдельной queued goal, а не переписывает активную. Сохранить возможность работать непосредственно в проектном топике.

Выход: два поручения разным проектам из одного топика независимо завершаются, сообщения/артефакты не смешиваются; неоднозначная реплика вызывает вопрос; повтор Telegram update не дублирует цель. Прямой project-topic ввод и inbox не создают двух владельцев.

На первом этапе неизвестный проект создаёт draft/request, а не автоматически provisioned инфраструктуру. Создание нового проекта/repo/topic — этап 4. Пользователь не обязан создавать топик для каждой мелкой идеи.

### Этап 4 — самостоятельное создание проекта и новые виды работ

Подключить проектный provisioner через команды; отдельно подтвердить, какие repo/topic операции предавторизованы владельцем. Создание проекта → repo → topic не одна внешняя транзакция: нужны receipts, возобновление после частичного успеха и reconciliation. Не удалять автоматически уже созданный repo с данными при ошибке следующего шага.

Research и другие work domains подключать по одному, с полноценным runtime handler и критерием результата. Установка стека — request → owner consent → provisioning → проверка готовности → inventory → wakeup. Наличие capability в тексте модели не равно установленному инструменту.

Выход: запрос исследования может создать разрешённый проект, получить настоящий результат и доставить его без ручной маршрутизации. Рестарт после создания repo не создаёт второй repo/topic. Внешние smoke только в отдельно разрешённых disposable targets.

### Этап 5 — параллельность и ограниченный live-пилот

Сначала независимые чтения/исследования, затем код/worktrees и дефицитные ресурсы. Добавить integration coordination и тесты из раздела 8. Не заменять последовательный безопасный режим глобально.

Live-пилот отдельно согласуется владельцем: проект, ветка, provider profile, допустимые расходы и эффекты. Сравнить несколько реальных целей с прежним режимом: число ручных вмешательств, достижение критериев, стоимость управления относительно работы, время и повторные ошибки. Цель не «модель много работала», а «владелец перестал быть диспетчером».

## 10. Обязательная матрица проверок

| Ситуация | Ожидаемый результат |
| --- | --- |
| Feature выключена, старые задачи и callbacks | Прежнее поведение, ни одного агентного запуска |
| Human button и agent command для одной операции | Один доменный контракт, разная policy, корректный actor в audit |
| Агент просит чужой проект, prod, секреты или owner waiver | Отказ без эффекта, понятная причина |
| Два старта: legacy + agent; два wakeup/две реплики | Один owner/пакет/turn, остальные события сохранены |
| Crash на каждой границе turn/command/outbox | Нет потерянной работы и дублирующего логического эффекта |
| Pause/revoke/scope change во время inference | Старый ответ не применяется |
| Job завершился прямо перед `wait_for` | Ожидание не зависает навсегда |
| Ошибка провайдера, невалидный tool call, unknown cost | Учёт сохранён, контролируемое ожидание/ошибка, не бесконечный repair |
| Gate/review на старый commit либо старые критерии | Нельзя принять новый результат |
| Пакет A окончательно не принят | Пакет B не стартует «потому что агент решил» |
| Последний элемент пакета в integration branch | Проходит только узкую delegated policy; default/prod всё ещё заблокированы |
| Один inbox, несколько целей, reorder/duplicate updates | Нет смешения контекста, дублей и неправильного проекта |
| Большая карточка, устаревшая кнопка, transport failure | Ограничения TG соблюдены; stale отклонён; delivery не меняет business state |
| Feature выключена посреди работы | Новые agent decisions запрещены; in-flight эффекты учитываются, legacy не перехватывает цель автоматически |
| Миграция с существующими live packages | Старые записи остаются валидными, их режим не меняется |

Для каждого выполненного этапа нужны unit tests, PostgreSQL integration и сквозной сценарий через настоящие границы. Unit mock, который сам записывает ожидаемый статус, не подтверждает работоспособность orchestration.

**Безопасность тестовой БД:** `tests/integration/conftest.py` завершает чужие подключения выбранной БД и делает TRUNCATE public tables. Использовать только новую выделенную disposable БД, явно заданную через `VUZOL_TEST_DATABASE_DSN`; до запуска проверить server/port/database и отсутствие production/shared данных. Не использовать default DSN вслепую. Integration skip из-за недоступной БД не считается успешной проверкой.

Использовать проектное воспроизводимое окружение и зависимости, не менять работающий production venv ради тестов. Для целевых прогонов можно отключать coverage threshold (`--no-cov`), но итоговый baseline/full-suite отчёт должен явно указывать команды, exclusions/skips и результаты. Не подключать настоящие платные модели, Telegram и production effects в default tests.

## 11. Отключение и откат

Feature flag по умолчанию off, opt-in по проекту. Отключение запрещает новые agent turns и mutations, включая уже полученный, но ещё не применённый ответ. Учёт и reconciliation выполняющихся эффектов продолжаются. Agent-owned goals остаются paused/waiting, а не автоматически передаются legacy sequencer на верхнем уровне.

Возврат существующего проекта в legacy — отдельная команда после settled effects и освобождения ownership. Внутри уже стартовавшего пакета соблюдаются существующие pause/cancel semantics; не бросать контейнеры и lease без владельца.

Миграции первой версии additive, с безопасными defaults для старых записей. Feature-off не равен rollback schema. Проверить совместимость старого бинарника с новой схемой либо дать отдельную подтверждённую процедуру восстановления. Не удалять новую историю и таблицы для «красивого отката». Backup/restore DB, config и внешних ресурсов требует отдельного плана; git branch возвращает только код.

## 12. Что Грок не должен делать заодно

- Переписывать executor, провайдеров, transport или workflow engine целиком.
- Ослаблять существующие review/approval/effect invariants ради зелёного демо.
- Давать агенту SQL, host-admin shell, owner credentials или repair CLI как обычные tools.
- Вводить новый HTTP сервис/очередь/agent framework без показанной необходимости.
- Убирать constraints базы ради многозадачного inbox.
- Начинать этапы 3–5 на недоказанном этапе 2 или мигрировать активные пользовательские проекты автоматически.
- Включать feature в production, деплоить Вузол, запускать paid live tests без отдельного разрешения.

## 13. Как сдавать работу

По одному связному этапу: реализация → тесты → отчёт → отдельный commit только после согласованного baseline. Не делать одного огромного коммита «новая архитектура».

В отчёте: baseline и итоговый SHA; выполненные этапы; схема изменённых границ; список миграций/config; точные тестовые команды и результаты; известные ограничения; инструкция включения/отключения в тестовой среде; демонстрационный trace «сообщение → goal → packages → evidence → итог». Не писать «готово», если проверен только tool adapter без настоящего исполнения.

Остановиться и запросить решение, если требуется расширить полномочия, разрушить старый контракт, изменить неподтверждённый baseline, трогать production или решить продуктовую неоднозначность, влияющую на безопасность. Если не хватает времени — оставить последний зелёный этап и точный список следующего шага. Ночная автономность не разрешает обходить blockers.

Главный критерий архитектуры: после рестарта можно из сохранённых фактов ответить, **чего хочет пользователь, кто сейчас отвечает за следующий шаг, что уже произошло и почему системе разрешено делать следующее действие**.
