# Карточки, подписки и уборка репозитория — 2026-10-22

## Короткий вывод

Переписывать Вузол не нужно. Но операционный долг реальный: настройки аккаунтов,
живой деплой и сообщения пользователю расходятся между собой. В этой проверке
найдены именно такие ошибки, а не проблема выбранного языка или нехватка ещё
одного архитектурного слоя.

Это целевой разбор карточек, учёта подписок, структуры репозитория и live-конфига.
Не полный построчный аудит всего проекта.

## Что найдено и изменено в коде

1. Сборщик перечислял только Codex/Grok. Pi/OpenCode не попадали в дашборд вообще.
   Теперь список строится из включённых CLI-профилей, независимо от наличия
   сборщика. API-профили с оплатой по запросу не выдаются за подписки.
2. Сохранённые строки лимитов не сверялись с текущим реестром. Удалённый или
   выключенный профиль мог оставаться на экране. Теперь список сверяется, а
   несколько моделей одного `account_id` дают одну строку аккаунта.
3. Добавлено `subscription_limits_visible=false`: можно скрыть истёкшую подписку
   без скрытого изменения маршрутизации задач. Поле не меняет execution revision.
   Если аккаунт больше нельзя использовать вообще, его нужно отдельно выключить
   в реестре и проверить назначения/фоллбэки; скрытие не делает этого за оператора.
4. У Grok B обнаружен лог от 4 августа, показанный как свежий октябрьский замер.
   Чтение старого файла обновляло `observed_at` сегодняшним временем. Теперь для
   логов используется время самого события; без времени или при возрасте больше
   15 минут остаток неизвестен. Свежесть persisted-снимков также проверяется.
5. Тип длинного окна терялся при сохранении: 24-часовой лимит мог называться
   недельным. `window_seconds` теперь сохраняется и читается из payload снимка.
6. Синхронный HTTP сборщика выполнялся прямо в async loop исполнителя. Сбор
   вынесен в ограниченную группу потоков: ожидание провайдера не блокирует event loop.
7. Подпись исполнителя показывала модель без аккаунта, иногда выбирая профиль
   планировщика/ревьюера. Карточки задачи и истории теперь показывают профиль,
   записанный аккаунт и модель рабочего шага. Карточка лида получает те же данные.
   Для новых CLI-запусков модель/effort фиксируются в runtime metadata до старта.
   Историческая неизвестная модель не восстанавливается из сегодняшних defaults.
8. Live-проверка нашла ещё ошибку сохранения версии дашборда: content hash
   сравнивался как возрастающий счётчик. Новый экран с численно меньшим hash
   доставлялся, но его версия не сохранялась. Теперь после успешного edit
   сохраняется точный hash; для task cards остаётся монотонная защита от старых
   изменений. Регрессионный PostgreSQL-тест сначала воспроизвёл ошибку.

## Что это НЕ чинит автоматически

- Pi/OpenCode обнаруживаются и видны, но численный остаток не реализован: текущий
  сборщик этого провайдера отсутствует. Будет честное «сборщик не подключён»,
  а не придуманные 100%. Нужен отдельный поддерживаемый источник измерений.
- Codex B/C настроены на приватные каталоги владельца с правами 0700/0600.
  Сервис сборщика не читает их авторизацию. Это не доказательство истёкшей
  подписки. Нужен переход на канонические service-state каталоги вместе с
  безопасным обновлением авторизации. Давать сервису доступ ко всему home нельзя.
- Grok B не предоставляет свежего измерения через проверенный текущий путь.
  Старый лог не помогает установить нынешний остаток или тариф.
- У Grok A владелец сообщил об отсутствии подписки. Скрытие строки — отдельное
  display-решение, не автоматическое снятие старых назначений на этот профиль.
- Обновлённый реестр подхватывается при обычной загрузке конфигурации сервиса;
  эта работа не добавляет hot reload во все процессы.
- Старые task cards обновляются по существующим событиям/запросам проекции,
  а не массовой перепубликацией всей истории после установки новой версии.

## Где действительно накопился долг

На момент проверки: около 95 тысяч строк Python в `src`, 117 тысяч в тестах,
311 исходных Python-файлов, 45 файлов миграций. Это измерение размера, не оценка
качества. `docs` содержит 84 файла и занимает около 772 КБ до этого отчёта.

### 1. Живой деплой — первый приоритет

У `repo-worker-1` в Compose labels перечислены **43 config files**. Состояние
установки восстанавливается последовательностью старых overlay, а не одним
понятным декларативным набором. Это практический источник «код поправили,
но другой процесс работает с другим значением».

Следующий отдельный шаг: получить `docker compose config` для всей установки,
сохранить приватный backup с прежними путями и правами, затем собрать небольшой
канонический base + production override. Перед заменой сравнить image, commands,
environment references, volumes/ACL, networks, ports, users, healthchecks,
restart/security/resource policies, все сервисы включая MCP и host-side units.
Не коммитить отрендеренные секреты. Проверить rollback. В этой задаче 43 overlay
не удалялись и не объединялись на ходу.

### 2. Документы смешивают настоящее и историю

`GROK_START.md`, `PROJECT_AGENTS_IMPLEMENTATION_PLAN.md`,
`PROJECT_LEAD_STAGE2_REVIEW.md`, `PROJECT_LEAD_R8_R9_REVIEW.md`,
`HANDOFF_PROJECT_ENVIRONMENT.md` — кандидаты на архив, не стартовые инструкции.
Добавлена карта `docs/README.md`, которая отделяет их от эксплуатации.

Безопасная следующая уборка: перенести согласованные исторические материалы в
`docs/archive/`, поправить относительные ссылки и оставить один актуальный
handoff для следующего агента. `GROK_FINAL_RESPONSE.md` не удалять по названию:
это описание действующего parser-контракта, связанное с regression tests.
`ASTRA_PRODUCT_CONSOLIDATION_HANDOFF.md` — незакоммиченный материал владельца;
не считать мусором. Старые пункты `BACKLOG.md` нуждаются в повторной проверке,
не в слепом исполнении или массовом закрытии.

### 3. Несколько механизмов выбора исполнителя

Role assignments и `project_executor_preferences` сосуществуют. У последнего
27 файлов с обращениями в коде/тестах; в production на проверке есть две строки
`mode=auto`. Из этого нельзя заключать, что механизм можно просто вырезать:
нужна также проверка pinned route, payload, открытых run и путей восстановления.

Порядок упрощения: один владелец нового выбора — role assignments; старые
preferences перевести явной миграцией; затем удалить совместимость вместе с
настройками/командами/тестами. Не добавлять третий слой выбора.

### 4. Слишком широкие модули

`telegram/projections.py` ~2500 строк, `telegram/delivery.py` ~1800,
`interpretation/service.py` ~1950, `providers/budgets.py` ~1800.
У них много причин меняться одновременно. Выделение по ответственности имеет
смысл при следующем изменении конкретного сценария; массовый перенос файлов
ради меньшего числа строк сейчас только расширит риск и diff.

## Что можно и нельзя убирать

- Кэши pytest/mypy/ruff, coverage и локальные build outputs уже игнорируются git.
  Это восстанавливаемые локальные данные, не продуктовая архитектура.
- `.venv` — локальное окружение, не закоммиченный мусор. Удалять его во время
  работающих процессов без проверки путей запуска нельзя.
- Fixtures с `jsonl`, схемы JSON, ADR, миграции, тесты recovery и сохранённые
  доказательства не удалять по расширению, возрасту или отсутствию UI-кнопки.
- Production worktrees, provider-state, ключи и runtime journals находятся вне
  этой уборки. Незавершённая paused-задача и её изменения не затронуты.
- Незакоммиченные reliability/MCP-правки не являются «лишним кодом».

Ничего материального в этой проверке не удалялось. Наибольший полезный следующий
шаг — сделать воспроизводимым деплой и привести аккаунты к service-state,
а не заводить новый репозиторий для нескольких сотен килобайт старых планов.
