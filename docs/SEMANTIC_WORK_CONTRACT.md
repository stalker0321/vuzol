# Semantic work contract

The semantic classifier proposes effect, relation, target, work domain and
operation. Runtime policy owns permissions, workflow selection, spending,
provider assignment and approval. An invalid combination is not permission to
substitute another requested outcome.

## Meaning

- `coding`: a repository implementation, including a website/app discussed in
  the conversation. Planning needed to implement it remains part of coding.
- `architecture`: an explicitly read-only repository design/analysis deliverable.
  It is neither a complexity class nor an automatic phase before implementation.
- `research`, `infrastructure`, `file_processing`: distinct work domains, never
  mapped to architecture as a fallback. Infrastructure keeps host-admin risk and
  confirmation policy; a semantic result does not grant privilege.
- `general`: conversation/status/controls, not an unspecified implementation.

An execute request with `general`, coding inspection/explanation/monitoring,
architecture modification/fix/deployment/monitoring, or research/file processing
deployment/monitoring is inconsistent with the current workflow vocabulary.
It produces clarification, no dispatch and no extra repair inference. The raw
choices, contract version and error are retained in the Jev receipt.

Explicit planning-only intent maps deliberately to a read-only design result.
This is separate from the removed blanket conversion of every non-coding task.
When a semantic effect is supplied, the legacy implementation-keyword list
cannot override its work domain. Legacy producers retain their old compatibility
policy; there are no new synonyms or phrase-specific overrides.

## Early executor readiness

Before workflow work, an explicitly assigned project/default CLI executor and
its permitted same-family fallbacks are checked using the existing eligibility
policy: type, role, capabilities, sandbox, launch mode, enabled state and pin.
The check never selects another family, weakens permissions or reserves budget.
Dynamic health, quota, concurrency, input/output size and spend remain claim-time
checks, so this is not a promise that a later invocation will be available.
Unpinned auto routing is still resolved at claim time.

Incompatibility blocks the workflow entry with `executor_route_unavailable` and
the assigned profile/type in its explanation. No context/worktree/model work is
started. Retry enters through the original predecessors, not directly at a
future executor step.

## Recovery of an unstarted misroute

`replace_unstarted_chat_work` accepts a freshly accounted, valid classification
against the original source and frozen spec. It requires the owner, current
task version/spec, enabled matching project topic, latest source/attempt, active
discussion, one route-blocked run, no provider invocation/reservation/spend,
no package materialization and no execution or unknown effects. Only internal
interpret/context/worktree preparation may have run. Source hashes are checked.

The old task/run are cancelled through normal transitions, old worktrees are
retained, and all interpretations/specs/usage remain intact. A linked child
task receives the same source and frozen discussion/document context, a new
interpretation and an audit receipt. No Telegram source message binding or raw
turn is rewritten or duplicated. The replacement is manual-start only: an old
Start does not authorize a newly interpreted implementation. Repeated recovery
returns the existing replacement and creates no duplicate work.
